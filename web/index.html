    ▪ sadbox

    Run AI coding agents in throwaway microVMs

    Every project gets its own isolated Linux microVM — a real VM with its own kernel — seeded from a local folder or a git repo, plus a full agent toolchain. Watch and steer the agent from your browser, gate its network access, and pull back only the work you approve. Your original folder is never touched.

    View projects →

    What you get

    🧊

    Isolated microVMs

    Each project is a real VM (Apple Virtualization.framework via container) — not a shared-kernel container. The blast radius stays inside the box.

    🤖

    Agents pre-installed

    Claude Code, omp, and opencode ship in every VM, alongside Bun, node (nvm), git, ripgrep and jq. They come from the base image — sadbox update (or sadbox setup) refreshes it. Log in once — sadbox keeps the logins and each project's history for the next VM.

    🖥️

    Browser terminal

    A live tmux session in your browser — watch the agent work and jump in anytime. Sessions survive supervisor restarts.

    🛡️

    Network firewall

    VMs have no network at all; their only way out is a filtering MITM proxy: block-by-default with time-boxed approvals, allow/block + header rules, and a live request log.

    🔑

    Vaults

    Variables and secrets, encrypted at rest, given to the projects you pick. A VM uses them without holding the real value — the proxy swaps it in on the way out.

    ↩️

    Reviewed sync-back

    Copy the VM's work into your folder as uncommitted changes — review with git diff and commit what you want. Your own uncommitted edits are never overwritten.

    Quick start

    1. 1
      Create a project. Give it a name, then either point at a local git repo folder or paste a git repository URL — sadbox seeds a fresh VM by copying the folder in, or by cloning the repo inside the VM.
    2. 2
      Open the terminal. From the project's detail page click Terminal ↗ and run claude, omp, or opencode.
    3. 3
      Approve network as needed. Egress is blocked by default; when the agent reaches a new host you'll get a prompt to allow it (once / timed / forever) on the detail page.
    4. 4
      Sync back. When you like the result, hit Sync back — the VM's files are copied into your folder as uncommitted changes, for you to review and commit.

    Good to know

    • Rebuild a project from its detail page to redeploy a fresh VM from the same source (folder re-copied or git repo re-cloned) — vault access, network rules and agent history are kept, and it uses the latest base image, so newly-baked tools show up.
    • Push to VM copies your folder's changed files into a running VM, the other way from Sync back. .env and .env.* files are never copied into a VM — not on create, rebuild or push. Put what they hold in a vault instead.
    • Add API keys, tokens and settings under Vaults, and tick the projects that may use each. A proxy item never enters the VM — it holds a placeholder the proxy swaps for the real value on the way out. A fetch item is read when needed: sadbox-vault get NAME (a secret asks you first; sadbox-vault list shows what a VM may use).
    • Claude Code: run claude and /login once, in any VM. sadbox keeps the login and refreshes it; every VM gets placeholders only, swapped for the real token on calls to Claude's API. API keys you enter in omp or opencode are copied into new VMs too; their OAuth logins are per VM. See Agents.
    • Agents' history (Claude, omp, opencode sessions) lives outside the VM, under the project's name — it survives Rebuild and Destroy, and a new project with the same name picks it up. Delete it under Agents.
    • Set default VM CPU / memory / disk and global network rules in Settings.
    • VMs have no network of their own: they cannot reach the internet, this machine, your LAN or each other except through the proxy's rules. Projects created before this show not isolated on their detail page until you Rebuild them.
    • The web UI needs a password (sadbox passwd to change it) and listens on localhost only; put a TLS reverse proxy in front before reaching it from other machines.

      1 Check the basics
      
          
      Run these once on the machine that will host the VMs. sadbox setup checks the
            dependencies, starts the VM backend and builds the base image (on Linux it also fetches Cloud
            Hypervisor and the guest kernel); it takes a few minutes the first time.
      
          
      sadbox setup          # build the base image, guest kernel and VM disk
sadbox doctor         # every check should be ✓, including "VM disk built"
command -v sadbox     # absolute path to use in a launchd job
      
          
      If a check fails, fix that first — starting, stopping and rebuilding
            projects all depend on the container service and the VM image.
      
        
      

        
      
          
      2 Run sadbox at login on macOS (launchd)
      
          
      sadbox serve runs in the foreground. A LaunchAgent keeps it in the background:
            it starts at login, restarts it if it exits, and writes its output to a log.
      
          
      Write ~/Library/LaunchAgents/dev.sadbox.supervisor.plist. Replace
            /Users/YOU with your home directory (launchd does not expand ~) and
            the binary path with the one command -v sadbox printed.
      
          
      <?xml version="1.0" encoding="UTF-8"?>
<!DOCTYPE plist PUBLIC "-//Apple//DTD PLIST 1.0//EN" "http://www.apple.com/DTDs/PropertyList-1.0.dtd">
<plist version="1.0">
<dict>
  <key>Label</key><string>dev.sadbox.supervisor</string>
  <key>ProgramArguments</key>
  <array>
    <string>/Users/YOU/.local/bin/sadbox</string>
    <string>serve</string>
  </array>
  <key>EnvironmentVariables</key>
  <dict>
    <key>PATH</key>
    <string>/usr/local/bin:/opt/homebrew/bin:/usr/bin:/bin:/usr/sbin:/sbin</string>
    <key>SADBOX_HOST</key>
    <string>127.0.0.1</string>
    <!-- named routes: also set SADBOX_ROUTE_DOMAIN (see section 4) -->
  </dict>
  <key>RunAtLoad</key><true/>
  <key>KeepAlive</key><true/>
  <key>StandardOutPath</key><string>/Users/YOU/Library/Logs/sadbox.log</string>
  <key>StandardErrorPath</key><string>/Users/YOU/Library/Logs/sadbox.log</string>
</dict>
</plist>
      
          
      Load it and watch the log:
      
          
      launchctl bootstrap gui/$(id -u) ~/Library/LaunchAgents/dev.sadbox.supervisor.plist
launchctl kickstart -k gui/$(id -u)/dev.sadbox.supervisor   # start (or restart) now
tail -f ~/Library/Logs/sadbox.log
      
          
      Open http://localhost:7070. The generated sign-in password is in
            that log and in ~/.sadbox/initial-password; change it with
            sadbox passwd.
      
          
      Checking, restarting after an update, stopping, or removing the job:
      
          
      launchctl print gui/$(id -u)/dev.sadbox.supervisor | head -20   # status
launchctl kickstart -k gui/$(id -u)/dev.sadbox.supervisor        # restart
launchctl bootout gui/$(id -u)/dev.sadbox.supervisor             # stop (VMs keep running)
rm ~/Library/LaunchAgents/dev.sadbox.supervisor.plist            # remove for good
      
          
        
            
      • Keep the PATH line. launchd does not inherit your shell's environment,
              and container, docker, colima and openssl
              are looked up on it.
        • 
            
      • Keep SADBOX_HOST=127.0.0.1 when Caddy or another IPv4 reverse proxy
              dials this machine. On macOS Bun's localhost binds ::1 only, so a
              proxy connecting to 127.0.0.1:7070 would get “connection refused”.
        • 
            
      • Never put SADBOX_PASSWORD in the plist — it is readable by anything
              running as you. The job uses the stored password from sadbox passwd.
        • 
            
      • After changing any environment variable, reload the job with
              launchctl bootout + launchctl bootstrap. kickstart -k
              restarts the process but keeps the old environment. Verify with
              launchctl print gui/$(id -u)/dev.sadbox.supervisor | grep SADBOX.
        • 
            
      • Apple silicon on macOS 15: add <key>SADBOX_DRIVER</key><string>vz</string>
              to EnvironmentVariables. Intel Macs do not need it.
        • 
            
      • Using colima? Run brew services start colima so Docker is up after a
              reboot; the first create or rebuild needs it.
        • 
            
      • Linux / WSL 2: use sadbox service install instead (a systemd user unit),
              then sudo loginctl enable-linger $USER if it should start before you log in.
              Logs: journalctl --user -u sadbox -f.
        • 
          
      
          
      Restarting or stopping the supervisor leaves running VMs alone — only the
            UI, egress proxy, approvals and port forwards go down.
      
        
      

        
      
          
      3 Put the UI behind Caddy
      
          
      sadbox speaks plain HTTP on 127.0.0.1:7070. The recommended shape is: run sadbox
            natively on the host, keep it on loopback, and let Caddy terminate TLS and reverse-proxy to it.
            sadbox has its own password sign-in; Caddy's basic_auth is an optional second layer.
      
          
      A standalone block on a hostname you control:
      
          
      sadbox.example.com {
    tls {
        dns cloudflare {env.CLOUDFLARE_API_TOKEN}
    }

    # optional second layer — sadbox has its own sign-in
    # basic_auth {
    #     admin $2a$14$REPLACE_WITH_BCRYPT_HASH   # caddy hash-password
    # }

    reverse_proxy 127.0.0.1:7070 {
        flush_interval -1        # stream the network feed (SSE) unbuffered
    }
}
      
          
      Or slot it into an existing wildcard block so the UI reuses a browser-trusted certificate:
      
          
      *.internal.example.com {
    tls {
        dns cloudflare {env.CLOUDFLARE_API_TOKEN}
    }

    @sadbox host sadbox.internal.example.com
    handle @sadbox {
        reverse_proxy 127.0.0.1:7070 {
            flush_interval -1
        }
    }

    # …your other per-host handle blocks…
}
      
          
        
            
      • Use a dedicated hostname or the root, not a subpath. sadbox serves its assets and
              API from /; named routes are the supported way to put apps on the same domain
              (each on its own hostname).
        • 
            
      • Caddy in Docker or colima: 127.0.0.1 in reverse_proxy is
              Caddy's own container. Use host.docker.internal:7070 (and
              host.docker.internal:7072 for named routes). With colima that usually resolves
              to 192.168.5.2; if it does not, add
              extra_hosts: ["host.docker.internal:192.168.5.2"] to the Caddy service.
        • 
            
      • WebSockets (the browser terminal) are upgraded automatically by Caddy v2 — no extra
              config. flush_interval -1 is what keeps SSE streaming instead of buffering.
        • 
            
      • Only proxy 7070 and, for named routes, 7072. Port 7071 is the egress
              proxy for older VMs; it refuses anything that is not a project VM and must never be exposed.
        • 
          
      
        
      

        
      
          
      4 Named routes (apps at their own hostnames)
      
          
      A named route maps <name>.<domain> to one port in a VM, through the
            same Caddy instance. It needs a domain plus a wildcard DNS record and certificate; the routes
            listener is loopback-only on 127.0.0.1:7072.
      
          
      Set the domain in the launchd job (or export it when running in the foreground):
      
          
      <key>SADBOX_ROUTE_DOMAIN</key>
<string>sadbox.example.com</string>
      
          
      Then give that domain a wildcard block. With SADBOX_ROUTE_DOMAIN=sadbox.example.com,
            sample.sadbox.example.com is one level below the UI, so it needs its own certificate:
      
          
      *.sadbox.example.com {
    tls {
        dns cloudflare {env.CLOUDFLARE_API_TOKEN}
    }

    reverse_proxy 127.0.0.1:7072 {   # Docker/colima: host.docker.internal:7072
        flush_interval -1
    }
}
      
          
      If your existing one-level wildcard (say *.internal.example.com) is dedicated to
            sadbox, you may instead set SADBOX_ROUTE_DOMAIN=internal.example.com: routes become
            sample.internal.example.com and reuse that certificate. Do not do that on a wildcard
            shared with other services — the routes listener would receive their hostnames too.
      
          
      Add a route from the project's detail page: Access → Named routes. Choose a name and the
            VM's port, then whether it needs a sadbox sign-in (default) or is open to anyone who can reach
            the hostname. Names are first-label DNS names; sadbox is reserved so a route can
            never shadow the UI. Named routes are HTTP/WebSockets only and do not support subpaths.
      
        
      

        
      
          
      5 Checks and troubleshooting
      
          
        
            
      • Caddy returns 502: it reached the Mac but sadbox is not listening where it dialled.
              lsof -nP -iTCP:7070 -sTCP:LISTEN should show 127.0.0.1:7070
              (not [::1]), and
              curl -sS -o /dev/null -w '%{http_code}\n' http://127.0.0.1:7070/
              should print 200.
        • 
            
      • Caddy exits instead of starting: run
              caddy validate --config /etc/caddy/Caddyfile --adapter caddyfile. An empty
              CLOUDFLARE_API_TOKEN fails at load with
              API token '' appears invalid.
        • 
            
      • The dns cloudflare challenge needs a Caddy built with
              github.com/caddy-dns/cloudflare: the official Docker image and Homebrew's
              caddy do not include it. Build one with
              xcaddy build --with github.com/caddy-dns/cloudflare. The zone_id
              option some examples show is not supported; scope the API token to the zone instead.
        • 
            
      • tls internal works on a bare LAN name, but every client must trust
              Caddy's root CA (caddy trust) or the terminal's wss:// is rejected.
              A real wildcard certificate avoids this.
        • 
            
      • Named routes show as off when SADBOX_ROUTE_DOMAIN is unset. If the
              routes listener could not bind, the supervisor log has the error and route URLs return
              502. Check that log after changing the environment and reloading the job.
        •

      Agents

    Run AI coding agents in throwaway microVMs

    Every project gets its own isolated Linux microVM — a real VM with its own kernel — seeded from a local folder or a git repo, plus a full agent toolchain. Watch and steer the agent from your browser, gate its network access, and pull back only the work you approve. Your original folder is never touched.

    What you get

    🧊

    Isolated microVMs

    Each project is a real VM (Apple Virtualization.framework via container) — not a shared-kernel container. The blast radius stays inside the box.

    🤖

    Agents pre-installed

    Claude Code, omp, and opencode ship in every VM, alongside Bun, git, ripgrep and jq. Open a terminal and run one.

    🖥️

    Browser terminal

    A live tmux session in your browser — watch the agent work and jump in anytime. Sessions survive supervisor restarts.

    🛡️

    Network firewall

    VMs have no network at all; their only way out is a filtering MITM proxy: block-by-default with time-boxed approvals, allow/block + header rules, and a live request log.

    🔑

    Vaults

    Variables and secrets, encrypted at rest, given to the projects you pick. A VM uses them without holding the real value — the proxy swaps it in on the way out.

    ↩️

    Reviewed sync-back

    Fetch the agent's commits into refs/remotes/sadbox/<name> with a diff preview — merge when you like it. Your worktree is never modified.

    Quick start

    1. 1
      Create a project. Give it a name, then either point at a local git repo folder or paste a git repository URL — sadbox seeds a fresh VM by copying the folder in, or by cloning the repo inside the VM.
    2. 2
      Open the terminal. From the project's detail page click Terminal ↗ and run claude, omp, or opencode.
    3. 3
      Approve network as needed. Egress is blocked by default; when the agent reaches a new host you'll get a prompt to allow it (once / timed / forever) on the detail page.
    4. 4
      Sync back. When you like the result, hit Sync back — the VM's files are copied into your folder as uncommitted changes, for you to review and commit.

    Good to know

    • Rebuild a project from its detail page to redeploy a fresh VM from the same source (folder re-copied or git repo re-cloned) — vault access and network rules are kept, and it uses the latest base image, so newly-baked tools (e.g. opencode) show up.
    • Set default VM CPU / memory / disk and global network rules in Settings.
    • Add API keys, tokens and settings under Vaults, and tick the projects that may use each. Inside a VM, sadbox-vault list shows them and sadbox-vault get NAME reads a fetch item.
    • For Claude Code auth, create a CLAUDE_CODE_OAUTH_TOKEN (or ANTHROPIC_API_KEY) secret in a vault and give the project access.
    • VMs have no network of their own: they cannot reach the internet, this machine, your LAN or each other except through the proxy's rules. Projects created before this show not isolated on their detail page until you Rebuild them.
    • The web UI needs a password (sadbox passwd to change it) and listens on localhost only; put a TLS reverse proxy in front before reaching it from other machines.

    Network allow / deny list

    Global egress rules applied to every VM. Block wins over allow; a host with no matching rule prompts for approval on first use. Per-project rules and header rewrites live on each project's detail view.

    Vaults

    Variables show their value here; secrets stay hidden until you reveal them. Tick the projects that may use an item.
